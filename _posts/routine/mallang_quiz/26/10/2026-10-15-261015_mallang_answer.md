- B. 매핑 DB는 모든 요청이 거치는 곳이지만, 과부하가 걸리더라도 단일 실패 지점(SPOF)이 되지는 않는다.

**정답: A**

**문제:** 빈칸을 채우시오.

프라우드넷의 RMI(원격 메소드 호출)에 대한 설명이다.

- RMI를 호출하는 쪽에서 함수 호출을 대신 해 주는 송신 측 코드(클래스)를 ① `___`(이)라고 한다. (영문 이름)
- RMI를 호출받는 쪽에서 메시지를 받아 해당 함수를 호출해 주는 수신 측 코드(클래스)를 ② `___`(이)라고 한다. (영문 이름)
- RMI 함수는 확장자가 ③ `___`인 파일에서 선언하며, 이 파일을 컴파일하면 송수신 코드 클래스가 자동 생성된다. (영문 대문자 네 글자)
- 수신 측 코드를 상속해 클래스를 만드는 대신, 함수나 람다식을 직접 넣어서 쓸 수 있도록 제공되는 클래스는 `CalcC2S::` 뒤에 ④ `___`를 붙여 쓴다. (영문 클래스 이름, ②로 시작함)

**📝 내 답:** RMIServer, RMIClient, ?, RMIClient_Impl(모름)

**정답:**

① Proxy
② Stub
③ PIDL
④ StubFunctional

**해설:**

함수 호출을 대신해 준다는 의미로 송신 코드를 proxy, 함수를 호출해 주는 기반이라는 의미로 수신 코드를 stub이라고 한다. RMI 함수는 PIDL 파일에서 선언하고 컴파일해 Proxy/Stub 클래스를 생성한다. `StubFunctional`은 함수나 람다식을 직접 넣어 쓸 수 있는 형태다.

## Q4. 🔴 어려움 — 🔺 8.5/10

**문제:** C++ RAII 클래스가 관리하는 자원을 외부에 노출하는 방법에 대해 답하시오.

```cpp
shared_ptr<Investment> pInv(createInvestment());
int daysHeld(const Investment *pi);

int days = daysHeld(pInv);   // 컴파일 에러
```

(1) 위 코드가 컴파일 에러가 나는 이유를 쓰시오. 그리고 올바르게 호출하려면 어떻게 써야 하며, 이처럼 호출하는 방식의 변환을 무엇이라 하는가?

```cpp
class Font {
public:
	explicit Font(FontHandle fh) : f(fh) {}
	~Font() { releaseFont(f); }

	FontHandle get() const { return f; }
	operator FontHandle() const { return f; }

private:
	FontHandle f;
};

void changeFontSize(FontHandle f, int newSize);
```

(2) `Font f(getFont());`가 있을 때 `changeFontSize(f, 12);`처럼 `Font` 객체를 그대로 넘겨도 컴파일되는 이유는 무엇이며, 이런 방식의 변환을 무엇이라 하는가?

(3) `Font f1(getFont());` 다음에 `FontHandle f2 = f1;`이라고 쓰면, 어떤 일이 일어나고 어떤 문제가 생기는가? (`f1`이 소멸된 이후를 포함해서 쓰시오.)

(4) 명시적 변환과 암시적 변환 중, 안정성 측면에서 유리한 쪽과 고객 편의성 측면에서 유리한 쪽은 각각 무엇인가? 또 어떤 성격의 자원일 때 암시적 변환을 피하는 것이 좋은가?

**📝 내 풀이:**

(1) shared_ptr을 포인터에 집어넣은 것, pInv.get(), 명시적 변환
(2) operator FontHandle()로 인해 FontHandle로의 암시적 변환 때문. 암시적 변환
(3) f2에 f1의 fonthandle이 복사된다. f1이 먼저 소멸되는 경우, f2가 이미 소멸된 값을 가진다.
(4) 안전성은 명시적, 편의성은 암시적이다. 서로 어떤 객체가 먼저 소멸될지 모르는 경우?

**정답:**

(1) `pInv`는 `shared_ptr<Investment>`인데 `daysHeld`는 `Investment*`를 받기 때문에 타입이 맞지 않아 컴파일 에러가 난다. `daysHeld(pInv.get())`처럼 `get()`으로 실제 포인터를 꺼내 넘겨야 하며, 이런 방식을 명시적 변환(explicit conversion)이라 한다.

(2) `Font`에 변환 연산자 `operator FontHandle()`이 정의되어 있어서 `Font` 객체가 `FontHandle`로 자동 변환되기 때문이다. 이를 암시적 변환(implicit conversion)이라 한다.

(3) 의도는 `Font` 객체를 복사하는 것이었지만, 암시적 변환이 일어나 `FontHandle`만 복사된다(`f2`는 `FontHandle` 타입). 그 결과 `f1`이 소멸되면서 `FontHandle`이 해제되면, `f2`는 이미 해제된 자원을 계속 가리키게 된다. 이는 자원 관리 객체의 목적과 상충한다.

(4) 안정성은 명시적 변환이 유리하고, 고객 편의성은 암시적 변환이 유리하다. 복사가 오용될 수 있는 자원이거나 자원을 명확히 관리하는 책임이 중요한 경우에는 암시적 변환을 피하는 것이 좋다. (단순한 포장(wrapper) 클래스라면 암시적 변환도 괜찮다.)

**🔍 피드백:**

- (1) 2.5/2.5 — 타입 불일치(`shared_ptr` ≠ 포인터), `get()`, 명시적 변환 모두 맞습니다.
- (2) 2.5/2.5 — `operator FontHandle()`에 의한 암시적 변환을 정확히 답했습니다.
- (3) 2/2.5 — `f2`에 핸들만 복사되고, `f1` 소멸 후 `f2`가 해제된 값을 가진다는 핵심은 맞습니다. 다만 "`Font` 객체를 복사하려던 의도와 달리 암시적 변환 때문에 `FontHandle`만 복사된다"는 점(자원 관리 객체의 목적과 상충)이 빠졌습니다.
- (4) 1.5/2.5 — 안정성은 명시적, 편의성은 암시적이라는 짝은 맞습니다. 암시적 변환을 피할 자원의 성격은 "복사가 오용될 수 있는 자원, 즉 자원을 명확히 관리하는 책임이 중요한 경우"입니다. "어떤 객체가 먼저 소멸될지 모르는 경우"는 (3)에서 본 증상(해제된 핸들 사용)과 연결되는 추측이지만, 자원의 성격을 말해 주는 표현은 아니라 부분 점수만 드렸습니다.
