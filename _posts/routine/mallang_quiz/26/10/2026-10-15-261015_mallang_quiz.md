## Q2. 🟡 보통

데이터베이스 샤드를 10개에서 11개로 늘리면 샤드 키를 해시한 값으로 샤드를 정하던 기존 방식에서는 리해시(기존 레코드의 재배치)가 발생한다. 이 문제를 피하기 위해 `입력(키) → 샤드 인덱스` 정보를 가진 DB를 따로 두는 **매핑 DB** 방식에 대한 설명으로 **가장 올바른 것**은?

- A. 샤드를 추가할 때 기존 레코드를 이동하지 않고, 새 샤드를 채우기만 하면 된다.
- B. 매핑 DB는 모든 요청이 거치는 곳이지만, 과부하가 걸리더라도 단일 실패 지점(SPOF)이 되지는 않는다.
- C. 샤드를 제거할 때도 매핑 DB와 유저 DB 모두 아무 변경이 필요 없다.
- D. 인증 서버는 ID를 해시 함수에 넣어 직접 샤드 인덱스를 계산하므로, 매핑 DB에는 질의하지 않는다.

> **출처:** `server/game_server/9/2026-03-26-game_server_10_2.md`

**📝 내 선택:** A.

B: SPOF가 되기에 문제가 생겼으며, 이런 경우 매핑DB도 분산하였다.  
C: 샤드를 제거할때 매핑DB에서도 연관된 페어를 제거하고, 유저 DB도 업데이트해주어야한다.  
D: 인증서버 - 매핑DB - 샤드를 거친다

## Q4. 🔴 어려움

C++ RAII 클래스가 관리하는 자원을 외부에 노출하는 방법에 대해 답하시오.

```cpp
shared_ptr<Investment> pInv(createInvestment());
int daysHeld(const Investment *pi);

int days = daysHeld(pInv);   // 컴파일 에러
```

(1) 위 코드가 컴파일 에러가 나는 이유를 쓰시오. 그리고 올바르게 호출하려면 어떻게 써야 하며, 이처럼 호출하는 방식의 변환을 무엇이라 하는가?

```cpp
class Font {
public:
	explicit Font(FontHandle fh) : f(fh) {}
	~Font() { releaseFont(f); }

	FontHandle get() const { return f; }
	operator FontHandle() const { return f; }

private:
	FontHandle f;
};

void changeFontSize(FontHandle f, int newSize);
```

(2) `Font f(getFont());`가 있을 때 `changeFontSize(f, 12);`처럼 `Font` 객체를 그대로 넘겨도 컴파일되는 이유는 무엇이며, 이런 방식의 변환을 무엇이라 하는가?

(3) `Font f1(getFont());` 다음에 `FontHandle f2 = f1;`이라고 쓰면, 어떤 일이 일어나고 어떤 문제가 생기는가? (`f1`이 소멸된 이후를 포함해서 쓰시오.)

(4) 명시적 변환과 암시적 변환 중, 안정성 측면에서 유리한 쪽과 고객 편의성 측면에서 유리한 쪽은 각각 무엇인가? 또 어떤 성격의 자원일 때 암시적 변환을 피하는 것이 좋은가?

> **출처:** `game_dev/cpp/chapter3/2025-06-11-cpp_3_15.md`

**📝 내 풀이:** (1) shared_ptr을 포인터에 집어넣은 것, pInv.get(), 명시적 변환  
(2) operator FontHandle()로 인해 FontHandle로의 암시적 변환 때문. 암시적 변환  
(3) f2에 f1의 fonthandle이 복사된다. f1이 먼저 소멸되는 경우, f2가 이미 소멸된 값을 가진다.  
(4) 안전성은 명시적, 편의성은 암시적이다. 서로 어떤 객체가 먼저 소멸될지 모르는 경우?
